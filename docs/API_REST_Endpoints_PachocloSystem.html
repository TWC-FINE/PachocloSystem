PachocloSystem · Sistema Hospitalario · Entrega del corte 2

1. Arquitectura

El sistema tiene dos microservicios Spring Boot independientes y un frontend Angular. Cada servicio tiene su propia base de datos PostgreSQL y no comparten código.

Frontend Angular ──HTTP + JWT──▶ PachocloSystem ──HTTP + X-Api-Key──▶ MedicamentosService (puerto 4200) (puerto 8080) (puerto 8081) Auth, pacientes, Inventario, stock trabajadores, usuarios, y vencimientos historial clínico
  • Frontend → PachocloSystem: todas las peticiones van a /api/** con el token JWT en la cabecera Authorization: Bearer.
  • PachocloSystem → MedicamentosService: comunicación HTTP real mediante RestClient (clase MedicamentosClient), autenticada con una clave compartida en la cabecera X-Api-Key. PachocloSystem es la única puerta de entrada a los medicamentos: el frontend nunca llama directamente a MedicamentosService.
  • Al crear un registro clínico de tipo medicación que indica medicamento y cantidad, PachocloSystem llama a POST /api/medicamentos/{id}/salidas de MedicamentosService para descontar el stock.
  • Si MedicamentosService no está disponible, PachocloSystem responde 503 y solo el módulo de medicamentos se ve afectado.

2. Convenciones HTTP

MétodoUso en la APIRespuesta exitosa
GETListar o consultar recursos. Los listados aceptan ?q= para buscar.200 OK
POSTCrear un recurso o registrar una operación (entrada/salida de stock, login).201 Created + cabecera Location
PUTReemplazar todos los datos editables de un recurso.200 OK
PATCHModificar un solo aspecto del recurso (habitación, rol, estado, contraseña).200 OK / 204 No Content
DELETEEliminar un recurso.204 No Content

Errores: 400 (datos inválidos), 401 (sin autenticar), 403 (rol sin permiso), 404 (no existe), 409 (conflicto), 503 (servicio de medicamentos no disponible).

5. Decisiones de diseño

  • Historial clínico sin PUT ni DELETE: un registro clínico es un documento médico y no se modifica ni se borra después de creado, para conservar la trazabilidad.
  • Usuarios sin DELETE: los usuarios se desactivan con PATCH /api/usuarios/{id}/desactivar en lugar de borrarse, para conservar la cuenta y poder reactivarla con PATCH /api/usuarios/{id}/activar. El sistema impide desactivar al último administrador activo.
  • Baja lógica de pacientes: DELETE /api/pacientes/{id} marca al paciente como inactivo en lugar de borrar la fila, para no perder su historial clínico. Desde ese momento la API lo trata como inexistente (404).
  • PATCH para cambios parciales: la habitación del paciente, el rol, el estado y la contraseña de un usuario se cambian con PATCH porque solo modifican un campo; PUT se reserva para editar el recurso completo.
  • Entradas y salidas de stock con POST: cada movimiento es una operación nueva sobre el inventario, por eso se crea con POST sobre /{id}/entradas y /{id}/salidas.
